# local-scan-for-secrets

Fast recursive secret scan of the **current working directory** — run it from
any folder you're about to commit, publish, or hand to someone.

## Usage

```sh
./scan-for-secrets.sh      # scans $PWD recursively (skips local secrets files)
./scan-for-secrets.sh -a   # also scan .env / *.env / .netrc / *.pem / ...
./scan-for-secrets.sh critical # audit: ~ dotfiles + ~/bin + ~/repos + tool config dirs + AI logs
./scan-for-secrets.sh mask     # dry run: where would your keys be masked
./scan-for-secrets.sh mask --apply # actually mask them
./scan-for-secrets.sh prune    # dry run: which AI session logs are >30 days
./scan-for-secrets.sh prune --apply   # delete them (run nightly by local-maintenance)
./scan-for-secrets.sh refresh  # dry run: which .env keys are out of date
./scan-for-secrets.sh refresh --apply # write the current values into them
./scan-for-secrets.sh refresh --here  # ...scoped to $PWD instead of ~/repos
scan-for-secrets           # alias in ~/.bash_aliases, works from anywhere
s4s                        # short alias
s4sc                       # short alias for the critical audit
s4sm                       # short alias for mask (s4sm --apply to execute)
s4sr                       # short alias for refresh (s4sr --apply to write)
```

> **Key source.** The exports moved out of `~/.bash_profile` into
> `~/.config/shell/env.sh` on 2026-08-25 so LaunchAgents could load them too.
> Both files are read, so mentions of `~/.bash_profile` below apply to either.
> Reading only the profile made every "YOURS" label, `mask` and the whole of
> `refresh` silently find nothing after the move.

`critical` mode scans the top-level dotfiles of `$HOME` (minus `.bash_profile`
— it is the key source and would match itself), `~/bin` and `~/repos`
recursively, the tool config dirs in `HOME_CONFIG_DIRS` — the scan's own
banner line lists them, which is the copy that cannot go stale; this sentence
used to name them and was still saying `~/.prism`, `~/.gito` after a third was
added — and the AI-assistant session stores (`~/.claude/projects`,
`~/.codex`, OpenCode, `~/.gemini`, Claude Desktop's session dirs) where
pasted keys and tool output accumulate, plus the agent scratchpad dirs
(`/private/tmp/claude-*/*/*/scratchpad` and the `$TMPDIR` equivalent). Those
are outside `$HOME` and are not session logs, which is why they went
unscanned: what lands there is a session's mid-task copy of a file, and in
practice that means backups of `~/.bash_profile` and `~/.config/shell/env.sh`
with live keys in them. `~/.google_workspace_mcp` is a special case worth knowing about: it holds one
OAuth token file per Google account, so it is scanned *and* its live
per-account files are sanctioned via `SECRETS_GLOBS`. Reporting the files the
server needs would be an alert nothing can action; reporting everything *else*
in that directory is the point, because a `.bak` or a hand-renamed leftover is
a live refresh token that nothing rotates and nobody remembers. Two such files
turned up the day it was added. That glob is a path, so it only bites under
`rg` — the `grep` fallback matches basenames — the same limitation as
`**/.auth/user.json`.

File-size cap is raised to 20M
there since transcripts are large; expect the scan to take a few minutes.
`.codex-global-state.json.bak` is sanctioned alongside the file it backs
up: codex rewrites it on every state save, so without the entry the weekly
scan reported the same JWT every Monday on a file nothing could action, and
deleting it just brought it back. `-a` still scans both.

Third-party checkouts and test fixtures full of sample keys are excluded
in this mode — the generic defaults are `CRITICAL_EXCLUDE_PATHS` in the
script. Your own additions (and extra sanctioned secrets globs) go in
`<config>/scan-for-secrets/scan-for-secrets.conf`, outside the checkout
(`<config>` is `$SYSTEM_TOOLS_CONFIG`, default `~/.config/system`): copy
`scan-for-secrets.conf.example` there and set `S4S_EXTRA_CRITICAL_EXCLUDE_PATHS`
and `S4S_EXTRA_SECRETS_GLOBS`, or point `S4S_CONF` at another file. Rule for adding: not your remote AND no local files of yours
inside (check gitignored files too — `git status` does not show a
dropped-in `.env`). ripgrep only, the grep fallback cannot path-exclude.

`mask` mode rewrites YOUR key values (the `~/.bash_profile` exports pass 2
searches for) to `<masked:$VARNAME>` — but only in files that are safe to
edit: `~/.viminfo`, shell history (`~/.bash_history`, `~/.zsh_history`),
the AI session log dirs above, and the agent scratchpads. Masking rewrites
in place on the same inode, so a scratchpad a live session is still using
keeps working. It also removes derived build output dirs under `~/repos`
(`.build`/`.next`/`.nuxt`/`.output` — regenerated by the next build, and a
classic place for secrets baked into bundles and run logs; plain `out` is
deliberately not auto-deleted, too generic a name), and prunes AI session
log files past their directory's retention (only from pure session-data
dirs: `.codex/sessions|archived_sessions` at 30 days,
`.codex/shell_snapshots` at 7, OpenCode storage, `.gemini/tmp` and the
Claude Desktop session stores at 30 — never a tool's root dir, which also
holds auth and config, and never `~/.claude/projects`, which Claude Code
deletes on its own `cleanupPeriodDays` schedule). Live credential
stores (`auth.json`, `settings.json`, `config.toml`, `oauth_creds.json`,
...) are never touched — masking them would break the tools that read
them. Default is a dry run printing per-file occurrence counts and the
prune tally (exit 2 if anything would change); `--apply` rewrites in
place, same-inode, so files a live session is appending to keep working,
and deletes the old logs. Strings matching the known credential patterns
(other people's keys, old rotated keys, JWTs, whole PEM blocks,
creds-in-URLs) are rewritten to `<masked:pattern>` as well — with the
URL-credentials class adapted so it cannot eat quotes/backslashes and
corrupt JSONL. Installed code, plugin docs, and live tool state under
the AI dirs are never touched (`MASK_EXCLUDE_PATHS` in the script), nor
are vendored and derived trees that turn up anywhere under a target —
`node_modules`, virtualenvs, build output, and `.git`, where rewriting a
byte corrupts the object store (`MASK_EXCLUDE_DIRS`). That list is
deliberately narrower than the scan's `EXCLUDE_DIRS`: a key sitting in a
`logs/`, `storage/` or `OLD/` dir still gets masked, because that is
exactly what mask is for.
Caveats: quit vim before masking `.viminfo` (vim rewrites it
on exit from memory), same idea for open shells and history files, and
masking is cleanup, not un-leaking — rotate any key that sat in these
files. A weekly automated `critical` scan runs via
`<config>/cron-jobs/jobs/secret-scan-weekly.job` (examples in `local-cron-jobs/examples/`) (Mon 07:00,
findings push to ntfy).

`prune` mode is the half of `mask` that is safe to run unattended: it deletes
AI session log files past their directory's retention and does nothing else —
`~/.claude/projects` is not one of those directories, because Claude Code
deletes its own transcripts on its own `cleanupPeriodDays` schedule. No masking
(that rewrites files a live session may still be appending to) and no build
dirs (removing a `.next` mid-workday is not maintenance). `local-maintenance`
runs it nightly, so the retention and the directory list stay defined here,
in one place.

`refresh` mode is the inverse of `mask`: after you rotate a key and update
`~/.bash_profile`, it pushes the new value into the files that are *allowed*
to hold keys, so every project picks up the rotation in one step. Scope is
`~/repos` recursively plus the `HOME_CONFIG_DIRS` tool config dirs
(`--here` for `$PWD` instead, which drops the config dirs), file types are
`.env`, `.env.*`, `*.env` and `.envrc`, and matching is by exact variable
name — the profile value of `OPENAI_API_KEY` replaces the `OPENAI_API_KEY=`
assignment, nothing else. A short alias map handles projects that spell a
key differently (`GOOGLE_API_KEY`/`GOOGLE_GENAI_API_KEY` → `GEMINI_API_KEY`,
`ANTHROPIC_API_KEY` → `CUSTOM_ANTHROPIC_API_KEY`); extend
`REFRESH_ALIASES` in the script, but only for the same credential.

### Service JSON configs

Env files are not the only place a launched service keeps a key. `refresh`
also visits a named list of JSON configs (`REFRESH_JSON_TARGETS`) — codexbar,
Zed, opencode and Claude Desktop today. They cannot be globbed for, so
adding a service means adding a line. Missing files are skipped silently, and
`--here` leaves them alone (they are outside any `$PWD` scope). A symlink to
one of these files needs no entry of its own.

Two ways a slot is matched:

1. **The JSON key name is the variable name** — an `env`/`environment` block
   like `mcpServers.raindrop.env.RAINDROP_ACCESS_TOKEN`. Matched
   automatically, no configuration.
2. **`REFRESH_JSON_MAP`**, for slots whose key name says nothing
   (`apiKey`, `token`, `Authorization`): a dotted path = variable name. List
   elements are selected by a sibling field — `providers[id=groq]` — never by
   index, because indices shift when the app rewrites its own config. A path
   is tried against every target file.

Where the stored value wraps the key (`"Bearer sk-…"`), only the last
whitespace-separated token is replaced. Rewrites are a byte-level swap of the
credential itself, not a re-serialization, so key order, indentation and
comments survive exactly — including JSONC files like Zed's, whose `//`
comments and trailing commas would otherwise be destroyed by a
parse-and-dump. If a file cannot be parsed even leniently, it is reported and
left alone rather than guessed at.

### GitHub Actions repo secrets

A rotated key can also live on GitHub, as an Actions repo secret consumed by
CI (`${{ secrets.SOCKET_SECURITY_API_KEY }}`). Names listed in
`REFRESH_GH_SECRETS` are handled on every `refresh`: the scope is scanned for
`.github/workflows` directories referencing `secrets.<NAME>`, each owning
repo is mapped to its GitHub slug via `git remote get-url origin`, and on
`--apply` the profile value is pushed with `gh secret set` (stdin, never
argv). GitHub's API never lets a secret value be read back, so the
stale/current verdict comes from a local stand-in: `.gh-secrets-state` next
to the script (mode 600, gitignored) records a salted SHA-256 of what each
push sent, per name and repo. Hash matches → current, nothing pushed; hash
differs or no record → push (dry run says which it would do and why). The
salt is random per push, so the state file cannot be used to confirm a
guessed key, and a failed push records nothing so the next run retries.
The push needs `gh` authenticated with access to the target repos. `--here`
skips this section along with the JSON configs.

What it deliberately will **not** do:

- **Write a git-tracked file.** A tracked `.env` is one that gets committed;
  putting a live key in it would create the leak this tool exists to find.
  Tracked candidates are listed as skipped and never opened for writing.
- **Touch templates** — `.env.example`, `*.sample`, `*.template`, `*.dist`,
  and `*.bak*`/`*.old*`/`*.orig` leftovers.
- **Add a variable or create a file.** Only an existing assignment of a
  matching name is rewritten, so refresh can never introduce a key into a
  project that did not already have one.
- **Overwrite an indirection or a placeholder.** `KEY=${KEY}`, `change-me`,
  `your-key-here`, `xxx`, `<...>` and empty values are reported and left
  alone — those are deliberate, and a real key does not belong there.
- Commented-out lines are not assignments, so they are never rewritten.

Quoting style (`KEY=v`, `KEY="v"`, `KEY='v'`), an `export` prefix and any
trailing comment are preserved; the rewrite is same-inode, so a symlinked
`.env` keeps pointing where it did. Default is a dry run listing the stale
variables per file **by name only** — a value is never printed, in either
mode — followed by a rolled-up `keys that would change:` list of the distinct
variable names (with `(in N files)` when one key is stale in several), so you
can see the blast radius without assembling it from the per-file output. It
exits 2 if anything is out of date; `--apply` writes, prints the same list as
`keys changed:`, and exits 0.
Values never reach argv or disk: they are passed to the rewriter through the
environment, same as `mask`. Names that merely contain `PAT` (`PATH`,
`GOPATH`) are excluded. A full `~/repos` sweep takes ~30s, most of it
walking the tree and asking git about each candidate.

### Which value wins, and which keys are off limits

`~/.bash_profile` is read **in file order**, and the last `export` of a name
wins — what the shell itself ends up with. (The scan passes sort their pairs;
refresh must not, or "last" would mean last alphabetically.)

A name exported more than once — typically an `if [ "$USER" = ... ]` branch —
gets a note listing the **last 4 characters of every value in file order**
plus the one being used, so the right branch is identifiable without opening
the file:

```
note: $GEMINI_API_KEY is exported more than once in ~/.bash_profile (…al6Y, …Nznc, …al6Y) — using the last, …al6Y
```

Four characters is the same order of disclosure as the scan output, which
prints the first 8 characters of a match. If the value live in your shell
differs from the file's (a conditional took the other branch, or you edited
the profile without re-sourcing), that is called out the same way — and the
**file wins**, since the point of refresh is to propagate what you just
edited.

A key **commented out** in `~/.bash_profile` is disabled on purpose —
`ANTHROPIC_API_KEY` is commented out *and* `unset` there so Claude falls back
to its own auth. Refresh never writes such a name anywhere, and never aliases
onto it; a file that has one is reported as `left alone (commented out in
~/.bash_profile, disabled on purpose)` rather than silently ignored. The rule
is per-name, not per-line: a name that is commented out in one place but
actively exported in another is live, not disabled.
Commenting an export out is therefore the way to take a key out of refresh's
reach.

By default the sanctioned local secrets files (`.env`, `*.env`, `.envrc`,
`.netrc`, `.npmrc`, key/PEM files, `credentials.json`, ...) are skipped —
they are *supposed* to contain secrets, so scanning them is noise for the
main use case ("am I about to commit/publish a secret?"). `-a`/`--all`
includes them. `.env.example` and `.env.production.example` are on that
skip list too, as are the AI tools' own live token stores (`auth.json`,
`oauth_creds.json`, ...) — the authoritative list is `SECRETS_GLOBS` in
the script. Known-fake fixtures are filtered from pattern findings (AWS
docs `...EXAMPLE` keys, URLs whose password is a `${VAR}`/`<name>`
placeholder or an obvious dev value like `*_dev_password` — see
`FAKE_FIXTURE_RE`).

Exit 0 = clean, exit 2 = findings (matches truncated to 8 chars — open the
file to see the rest; the scanner never prints a full secret).

## What it scans for

1. **Known credential formats** — OpenAI (`sk-proj-`, `sk-ant-`), GitHub
   (`github_pat_`, `ghp_` family), GitLab, AWS access keys, Google API keys
   and OAuth tokens, Slack, Hugging Face, npm, `sts_` service/ingestion keys, Stripe,
   Square, SendGrid, JWTs, private-key PEM blocks, and `scheme://user:pass@`
   URLs.
2. **Your actual keys** — at runtime it reads `~/.config/shell/env.sh` and
   `~/.bash_profile` (env.sh first, the order a shell sources them; a missing
   file is skipped), takes the values of every exported variable whose name
   contains `KEY|TOKEN|SECRET|PASS|PAT|CRED`, and searches for those literal
   strings.
   Catches a personal key pasted into a config even when its format isn't in
   the pattern list. Values never appear in output — findings are reported by
   variable name.

Each pattern finding is labeled with what the prefix identifies when known —
`[OpenAI project API key]`, `[GitHub fine-grained PAT]`, `[AWS access key
ID]`, `[sts_ service/ingestion key]`, `[JWT]`, ... — so you can see at a
glance what kind of credential leaked.

Findings that are YOUR keys are additionally highlighted in both passes:
pattern-scan hits matching a `~/.bash_profile` value get a red
`<<< YOURS: $VARNAME (~/.bash_profile)` tag, and pass 2 lines are prefixed
`YOURS: $VARNAME`. An untagged finding is a secret that is *not* one of
your exported keys — someone else's, a service key, or an old rotated one.

## Speed / scope

Uses ripgrep (`grep -rEI` fallback): binaries auto-skipped, files >1MB
skipped, plus excludes for `.git`, `node_modules`, `.venv`, data/log dirs,
lockfiles, archives, and media. `mask` shares the glob excludes and skips
vendored/derived trees too, but keeps the data/log dirs in scope — see
`MASK_EXCLUDE_DIRS` above. Gitignored files and dotfiles ARE scanned —
that's where secrets live. Whole `~/repos/system` scans in ~0.3s.

## The local judgment of each hit (sd:2761)

When `jev` is on PATH, each durable pattern hit is asked of the local Kev:
is this a real credential, not a test value or placeholder? The call uses
`jev --local-only`, so a hit reaches Kev on loopback or nothing; it never
goes to Jev or another hosted model. The hit reaches `jev` on stdin, never
in argv.

The answer is recorded and not used. The scanner's own verdict is the shadow
answer, so the output and the exit code stay exactly as without `jev`.
`sd-db.sh judgments compare --stage JEV_SECRET_SCAN` reports how often Kev
agrees.

| Variable | Default | Meaning |
| --- | --- | --- |
| `JEV_SECRET_SCAN` | on | `0` switches the stage off |
| `S4S_JEV_MAX_HITS` | 10 | hits asked per run |
| `S4S_JEV_TIMEOUT` | 5 | seconds per call, no retry |

**Ledger subject and run (sd:2953).** Each `noul` passes `--subject secret-scan:<16 hex>`: the first 16 hex of the sha256 of the hit's `path:line`, followed by a newline. The matched text is never hashed, so no credential has a fingerprint in the ledger. An outcome recomputes it from the report with `printf '%s\n' PATH:LINE | shasum -a 256 | cut -c1-16`. Every call of one scan shares `JEV_RUN=secret-scan-<UTC yyyymmddThhmmss>-<4 hex>`, or the scan's inherited one.

## Accepted exposure (2026-09-21, sd:1254)

The weekly `critical` run has exited 2 every Monday since 2026-08-24 on real
findings, and the operator has ruled on them. Recorded here so the ruling is
legible rather than re-argued each Monday.

- **The exposed key values are accepted, not rotated.** They sit in plaintext
  under `$HOME` on a single-operator machine with FileVault on, and the
  directories that hold them are mode 700 (`HARDEN_DIRS` in
  `local-machine-setup`). No third party has local account access, so the
  exposure class is "readable by a process running as this user", which
  rotation does not change.
- **`~/.codex/shell_snapshots` is a cache, not a record.** Codex writes a
  fresh snapshot of the whole exported shell environment on every session
  start. Measured 2026-09-21: 6 files, newest minutes old, oldest two days,
  on a machine that has run codex for months. It is classified TRANSIENT in
  `critical` (`TRANSIENT_PATH_RE`) and pruned at 7 days, the same treatment
  the agent scratchpads get and for the same reason — an alert nothing can
  action is not a finding. Classified, not excluded: an entry in
  `CRITICAL_EXCLUDE_PATHS` would drop the directory from both passes even
  under `-a`, hiding a value that has since left `env.sh` but is still in an
  old snapshot. Transient keeps every match printed and only declines to
  page. The pattern is anchored at the start of the `$HOME`-relative path,
  so a committed `repos/<project>/.codex/shell_snapshots/` copy stays
  durable and still exits 2 — nothing regenerates or prunes that one.
- **Retention purging addresses accumulation, not this finding.** Measured
  before the ruling: at a 30-day cutoff, 27 of 10890 files under
  `~/.claude/projects` and 160 of 1603 under `~/.codex/sessions` are
  deletable; at 90 and 180 days, nothing at all. Over 99% of transcripts are
  under 30 days old and nothing on the machine is older than 90, so the
  exposed material is in current, active work and no retention window reaches
  it. Do not read the prune as remediation of the exposure.
- **Still open.** The transcript findings themselves (~1340 durable pattern
  hits under `~/.claude/projects` and `~/.codex/sessions`) are unchanged by
  any of the above, so `critical` still exits 2 and the Monday alarm still
  fires. The actionable remediation for them is `mask --apply`, which rewrites
  the values in place on the same inode; it has not been run and needs an
  operator decision, because it rewrites files live sessions may still be
  appending to.
- **`~/.bash_history` stays in scope.** The 2026-09-21 run flagged four lines
  carrying `sts_` ingestion keys. It is not excluded, because the
  finding is actionable without deleting anything: `sts_[0-9a-f]{20,}` is in
  `PATTERNS`, `PATTERNS` drives `mask`, and `.bash_history` is a `mask`
  target, so `mask --apply` rewrites those values in place. An exclusion
  would hide a finding that has a one-command fix. (The file itself
  disappeared later the same day, leaving a zero-byte
  `~/.bash_history-<pid>.tmp` beside it, which is consistent with a failed
  atomic history rewrite. Cause not established. That is a separate
  problem; it does not change the rule.)

## Gotchas

- With `-a`, findings in gitignored `.env` files are *expected* — that's the
  sanctioned place for secrets here. Worry when a finding is in a tracked
  file, which is exactly what the default (no `-a`) mode shows.
- Pass 2 only knows keys exported in `~/.bash_profile`; keys that live only
  in `.env` files are covered by pass 1's format patterns.
- `grep` fallback has no file-size cap (grep can't); with ripgrep installed
  (it is, via homebrew) this never applies.
