# Dashboard runtime

The production launcher uses the command pack's provisioned Python interpreter
and its installed `sd_db` build. It runs in isolated mode: a caller's
`PYTHONPATH`, current directory, and neighboring `local-sd-db` source checkout
cannot replace that library. `test` is the explicit source-development path.
The installer never provisions or downgrades the library. Install the matching
build and migrate the database separately before replacing the dashboard.

For a local-only service, create an explicit JSON configuration such as
`~/.config/sd/dashboard.json`:

```json
{"port": 8767}
```

An optional `database` field names an absolute database path. Without it the
database is `~/.local/share/sd/sd.db`. The provider controls read the registry,
`providers.yaml`, from the folder that holds the database; a missing file is a
`RegistryError` naming that path. `SD_DASHBOARD_PYTHON` may select another
provisioned interpreter; its `sd_db` must be an installed package within that
interpreter, and its schema must match the database.

Review the exact runtime, database, replacement LaunchAgent, and fingerprint:

```sh
./dashboard.sh preflight --config ~/.config/sd/dashboard.json
./dashboard.sh install --config ~/.config/sd/dashboard.json
```

Both commands only inspect state. To apply the reviewed plan, use its exact
fingerprint:

```sh
./dashboard.sh install --config ~/.config/sd/dashboard.json \
  --apply --expected-fingerprint REPLACE_WITH_REVIEWED_FINGERPRINT
./dashboard.sh health --config ~/.config/sd/dashboard.json
```

Changes to the configuration, installed library bytes, dashboard package or
launcher bytes, loaded status, old plist, or Serve configuration invalidate the
plan. Build digests enumerate the installed library's regular source/data files
and the dashboard package, including static assets, plus the fixed Ports
dependencies `collectors.py` and `../local-machine-setup/machine-setup.sh`;
generated bytecode is excluded. The installer backs up the old plist
and the complete preflight report under
`~/.local/share/sd/runtime-backups/dashboard-*` before replacing
`~/Library/LaunchAgents/<prefix>.sd-dashboard.plist` (prefix from
`SYSTEM_TOOLS_LABEL_PREFIX`, default `local.system-tools`). The new service must return
`/health` with the expected schema, library path, and build digests, and its
process ID must match the newly loaded LaunchAgent. Health reports the build
captured when the server started and becomes unhealthy if its files change;
an older process cannot claim the new bytes just installed. A server started
with `--config` rechecks those files every 30 seconds. When they change and
`dashboard.sh preflight` passes for the new build, it exits, and the
LaunchAgent's `KeepAlive` starts the new code. A failed preflight keeps the old
build serving and logs one line; an installed sd_db behind the checkout waits
for the pack's `make setup`, whose new library bytes retry it. An ordinary
installation failure restores the previous plist and reloads its service when
it was previously loaded. Process termination or machine failure can require
manual recovery using that backup; the installer does not claim crash-atomic
replacement across launchd, files, and Tailscale.

Local-only installation never invokes Tailscale. The browser URL is
`http://127.0.0.1:8767` for the configuration above.
The generated launch environment includes the standard system tool directories
needed for listener inspection. It also carries the
installing shell's `sd` directory and `OBSIDIAN_VAULT`, which Notes' quick
notes need (sd:2549); `install` prints one line for each it cannot find, and
still installs. Operations' service controls act only on
eligible user LaunchAgents; system daemons and dashboard/access services remain
read-only. See [README.md](README.md) for the Operations tabs, one per entry of
`operations_screen.AREAS`, and their scope. Today's Now section reads the fleet
child (both areas), the shadow table and the launchd jobs on each `/api/now`
request a page makes, not on the page render; a fleet child or a jobs read that
fails is a row on Now.

## Private front door

The runtime can also install a private route for the server's authenticated
front door. Keep this configuration in a separate file such as
`~/.config/sd/dashboard-private.json`; retaining the original local-only
configuration lets the old LaunchAgent use it during rollback.

A private configuration explicitly pairs `origin` with `operator_login`, for
example `https://YOUR-NODE.YOUR-TAILNET.ts.net:8443` and the node owner's exact
Tailscale login, plus the backend `port`. Preflight verifies the current node,
owner, HTTPS listener, exact loopback proxy, and absence of Funnel on that
authority. It refuses another service already occupying 8443. The installer
adds only that route when missing; it never changes the existing 443 service,
resets Serve, or enables Funnel. If unrelated Serve configuration changes
during installation, it refuses the replacement. Rollback removes only a route
this attempt added, and preserves a route edited concurrently for manual review.
Disabling the mount repeats the original `--bg --https=8443 --set-path=/`
flags, as required by the [Tailscale Serve CLI](https://tailscale.com/docs/reference/tailscale-cli/serve#disable-tailscale-serve).
A timed-out creation is checked against current Serve state before cleanup.
Removal must be observed, and unrelated Serve configuration must remain intact;
an accepted CLI command alone does not prove rollback succeeded.

Before replacing or rolling back a LaunchAgent, the installer checks its exact
plist bytes and the loaded command identity. A concurrent operator change is
preserved and reported for manual recovery, together with the backup path.
After requesting shutdown, it waits for launchd to confirm removal before replacing
or restoring the plist. Each wait has a ten-second deadline and rechecks ownership.
An unresolved shutdown preserves the files and reports manual recovery.
The associated route is also retained when service ownership is uncertain.
These checks do not make changes to launchd, files, and Serve one atomic
transaction; avoid concurrent runtime reconfiguration during the rollout.

The backend binds loopback. A private route requires server-side validation of
the proxy identity, configured operator, request origin, session, and CSRF token;
creating the route by itself does not provide authenticated workflow access.

## Direct Tailscale IP access

To avoid browser DNS resolution, add `ip_origin` to a private configuration:

```json
{"origin":"https://YOUR-NODE.YOUR-TAILNET.ts.net:8443","operator_login":"YOUR-LOGIN","port":8767,"ip_origin":"http://YOUR-TAILSCALE-IP:8768"}
```

Replace `YOUR-TAILSCALE-IP` with this node's IPv4 address from `tailscale ip -4`.
The address must belong to the running node and fall within `100.64.0.0/10`.
Use the same preflight and fingerprinted installation commands shown above.
The existing loopback backend and HTTPS route remain available.
The additional HTTP listener binds only the specified Tailscale IP on port 8768.
It does not create a Serve route or expose a LAN listener.

Each request resolves its TCP peer through `tailscale whois --json --proto=tcp`.
Only the configured operator can access the dashboard.
Tagged devices, forwarded identity headers, and unavailable identity evidence are refused.
The peer rules live in `sd_db.tailnet`, which `sd-db.sh serve` shares; the installed library must carry that module.
The current node address and absence of a conflicting Serve listener are checked on each remote request.
Session expiry, operator and origin binding, CSRF, HttpOnly, and SameSite remain enforced.
The IP origin uses HTTP, so its cookie omits the browser's Secure attribute.
Network traffic still travels over the encrypted Tailscale connection.
See [Tailscale server guidance](https://tailscale.com/docs/servers).

Health reports `ip_origin` only while its listener thread is running.
The installer requires that confirmation before accepting the replacement.
Then open the literal IP URL from a connected Tailscale device.
Listener health does not establish browser reachability through the host's network policy.
Verify the selected `SD_DASHBOARD_PYTHON` interpreter; another Python installation can have different network access.
An alternative runtime must contain the matching installed wheel and pass the dashboard suite before replacement.
This access option does not migrate the database or replace the installed library.

## Verification

`./dashboard.sh test` includes installer tests with disposable files, a fake
launchd service, and fake Tailscale state. These prove preview behavior, rollback,
stale-plan refusal, preservation of a public 443 Funnel, no Tailscale dependency
for local mode, and isolation from an injected `PYTHONPATH`. They perform no
live installation. A live rollout still requires checking the returned
`/health` response and the actual browser experience.


## Workflow controls

Skills reads the installed pack receipt and its `skills/`, `contrib/` and
`skills/paths.json` files at runtime. Trials are database rows; the next pack
installation renders them. Review, promotion, demotion and accepted proposals
queue isolated runner work. They never move files or create branches in the
operator checkout. Review proposals carry the source snapshot and actual
reviewer identity; all latest author vendors are excluded.

Tasks queues a revision-bound selection sequentially or in parallel; an item page queues its one item.
Tasks need a registered repository and an item branch. A new branch is bound to
the verified remote default head during preparation, then created only in the
runner clone; changed source heads and branch collisions refuse the start. Runner cancellation, resume and restore use the installed
`<prefix>.sd-runner` LaunchAgent definition even when its daemon is stopped.
Only the generated argument shape, owned service files, provisioned interpreter
and matching database are accepted. Requests bind the exact assignment revision
and attempt UUID. Resume requires a resolved kept checkout; restore copies into
a new destination. Neither action deletes retained work.

Operations renders one area per entry of `operations_screen.AREAS`.
[README.md](README.md) names them, and no list here repeats that inventory.
Usage's month section and `/api/usage` (`usage_screen.py`) read
`sd_db.usage.read` -- `reads.usage_month` under the registry's merged caps, so
a legacy row cap on a `start` bill is no cap there, as on the cost tile
(sd:234 slice 12h) -- on the request's read-only connection and write
nothing; the orphan sweep that `sd-db.sh usage` runs is the verb's alone. Provider enabled flags and both role orders save together, after the
complete proposal passes the author/reviewer guard. Resources reuse bounded
read-only collectors; research configuration is parsed as data, never executed.
The obsolete Obsidian Skill Proposals action is replaced by the Skills workflow.
Re-run collector on Contributions and Health runs `sd_db.sync_shadow` for each tracker in a server thread (sd:2207, sd:2894, `shadow_run`).
A run has one 120-second deadline; a Jira request in flight may take 30 seconds more.
A second start is refused while a run is live, or while another `sd shadow sync` holds the library's shadow-sync lock.
A satellite refuses a start: the lock sits beside the hub's database file.
The run calls `gh` with the LaunchAgent's environment; gh's keychain login under launchd is not yet verified.

Completed scheduled jobs call `sd reports ingest` once with their run identity,
log offset, times and exit code. Existing job output, emails and notifications
continue. Every run records a heartbeat, the job's health. A report item exists
only for an event. A failed job or explicit `SD_REPORT_ATTENTION: reason` line
files a report with a followup. The same failure again, while that report is
open, adds to its repeat count instead. A clean run after a failed one files a
recovery report. A quiet success writes the heartbeat and no report. Success
is still not a claim that no findings exist; a job states findings with the
marker. A replayed run identity writes nothing new. If database ingestion
fails, the job keeps its original exit code and names the source log, offset and
run identity for manual replay. No extra scheduler or notification is started.
Progress counts recorded requests, finished review attempts and recorded
deliveries; these observations do not measure human effort or adoption.

Focused checks use disposable state:

```sh
PYTHONPATH=../local-sd-db:.:tests python3 -m unittest discover -s tests -t . -v
```

The service process-group and retained-clone checks live in the runner suite.
The dashboard HTTP suite substitutes the native service boundary while checking
authentication, revisions, exact attempt identity, unavailable installation,
atomic batches and non-overwriting restore destinations. A physical iPad
interaction remains an operator check.
