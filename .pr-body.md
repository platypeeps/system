## Summary

- system sd:8579 — new component `local-fseventsd`, entrypoint
  `fseventsd.sh`, verbs `status|repair|check|test|help`. On 2026-11-11
  fseventsd held 28.77 GB resident against Apple's own footprint
  budget of about 30 MB, with swap at 19.70 of 20.48 GB and pressure
  level 2 (fleet sd:8557). There is no vendor fix, and System
  Integrity Protection refuses `launchctl kickstart` on the daemon,
  so TERM is the whole repair.
- system sd:8579 — two questions, never folded into one answer. Is
  the daemon oversized, against `FSEVENTSD_RSS_MB`? Is the machine
  hurting, meaning `kern.memorystatus_vm_pressure_level` above 1 or
  `vm.swapusage` used over `FSEVENTSD_SWAP_MB`? That second number is
  8192 because `health-check.sh` already uses it. Every line answers
  both, and each caller reads the one it needs. `status` exits 1 on
  the resident size alone, so the nightly sweep can name an oversized
  daemon before the machine starts swapping. Only `repair` reads the
  machine's answer, because the TERM drops the FSEvents history that
  every backup and indexing tool reads, and it signals only when both
  answers are yes.
- system sd:8579 — a sysctl that does not answer leaves the machine's
  question unknown, which is neither a yes nor a no: the line says
  so, and `repair` sends no TERM and exits 1 while the daemon is
  oversized.
- system sd:8579 — the help text carries the phrase
  `local-health-check`, which is how the nightly status sweep
  discovers a tool, so `health-check.sh` is unchanged. `status` exits
  3 when `FSEVENTSD_RSS_MB` is unset, off Darwin, or with no daemon,
  so a machine with nothing set up stays silent; the first line
  always starts with the resident size, so the trend shows on a
  healthy machine too and the sweep has its remedy text.
- system sd:8579 — the daemon is read with `pgrep -x fseventsd` and
  `ps -o rss= -p`, the reading
  `docs/work/2026-11-04-ramdisk-tmp/design.md:134` already used on
  this daemon, and with no `comm` column at all. A pid `pgrep` names
  and `ps` cannot read is skipped, not reported as a daemon of no
  size.
- system sd:8579 — `repair` signals through
  `sudo -A /usr/bin/pkill -TERM -x fseventsd`, the exact command and
  arguments of the new `machine-setup-repairs.sudoers.example` line.
  pkill by name and not kill by pid, because a pid argument would
  need a wildcard in that line, and a wildcard there allows any pid.
  `FSEVENTSD_MIN_HOURS`, default 6, is the rate floor, recorded in
  the XDG state folder and not in the config folder, which holds
  values only (convention 3, sd:3990).
- system sd:8579 — `examples/profiles/common.cron` and
  `local-cron-jobs/examples/fseventsd-hourly.job` put `repair` on
  every machine's hourly slot. Each machine's real profile lives in
  the config folder outside the checkout, so this wires the example
  `common.cron`, the kind machine-setup layers onto every profile.
  The README's install lines make both config folders before they
  copy into them, as every sibling README does.
- system sd:8551 — one entry, `repos/**/*_tests.*`, added to
  `CRITICAL_EXCLUDE_PATHS`. Rust and Go name a test module after the
  thing it tests, which `repos/**/*_test.*` does not match, and every
  durable finding of the 2026-11-09 weekly scan was a placeholder in
  such a file. The entry ends at `_tests.`, so
  `integration_tests_helper.rs` is still scanned, a placeholder in a
  source file still pages, and `/private/tmp` stays scanned with its
  scratchpad hits still transient.

## One verdict for two questions, and every place that read it

The class: `fs_judge` folded "is the daemon oversized" and "is the
machine hurting" into one exit code, so no caller could ask its own
question. Every instance in the code, not only the ones review named.

| Instance | What the fold did | Now | Test |
| --- | --- | --- | --- |
| `run_repair`'s guard | read code 0 with `fs_hurting=yes` still set, so a daemon inside its budget was TERMed whenever another process drove swap or pressure up, once every `FSEVENTSD_MIN_HOURS` | reads the state, the size answer and the machine answer separately; no TERM unless the size answer is yes | `test_a_daemon_within_budget_is_never_termed_however_bad_the_machine_is` |
| `status`'s exit code | exited 0 for an oversized daemon on a quiet machine, and the sweep prints nothing for 0, so the nightly check could not name one until the machine swapped | exits 1 on the size alone | `test_a_high_size_alone_exits_1_on_a_quiet_machine` |

| `run_repair`'s exit 3 | came from `fs_code`, which also carried 1 for a broken setting | comes from the state | `test_repair_sends_no_term_with_no_daemon`, `test_a_bad_setting_is_broken_not_unconfigured` |

Measured, and it corrects the round-1 reading of the `comm` column.
The round asked for the change because no tty makes `ps` fall back to
79 columns, which would have cut the daemon's 134-character path in
every unattended run. On Darwin 27.2.0 `ps` cuts its lines to the
window only when it writes to a terminal: 41 characters at 40
columns, 80 at 79, 101 at 100, and the full 134 through a pipe or a
file, with or without `COLUMNS`. The old reader piped `ps` into
`awk`, so its output was never a terminal, and it found the daemon at
40, 80 and 200 columns and through a pipe. The reader was therefore
not broken; the new form is a simplification onto the repository's
own precedent, and it carries a guard test, not a fail-first one.
`lib/mas_app.sh:94` compares a `ps -o comm=` path the same way and is
safe for the same reason, a command substitution being a pipe; it is
filed as system sd:8580 to stop reading a `comm` column at all.
